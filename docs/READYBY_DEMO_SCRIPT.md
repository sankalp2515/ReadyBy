## Recording prerequisites

- All quoted times are generated by the implemented engine on the canonical fixture, not text embedded in the UI.
- Verify actual generated schedule order. If deterministic tie breaks choose an equally valid alternative, update the narration or fixture policy; do not fake the timeline.
- Real AI handles natural input. Typed input is sufficient for the simulation; voice is optional. If using voice, capture a visible transcript and distinguish web speech from native Alexa.
- Show any injected state/time progression with explicit captions. At 08:06, bag/lunch are reported complete; breakfast/bottles are active. Do not secretly preseed those facts and imply the live utterances caused them.
- Save a clean-reset recording and an alternate input recording. Show the bound recalculating when washer wait changes; avoid a demo that only accepts one exact phrase.
- Reload proves browser persistence. Also test server restart and include its result in evaluation evidence; do not describe reload alone as proof of restart durability.
- Use actual generated evidence and tool receipts. Show test results only after running them; include failures and limitations in the repository report.

## What the interface must make obvious

Before delay: departure time, two next actions, washer release, and planned finish.

After delay: why the full goal misses departure, which work is already done, and which single optional task can move.

Before approval: a preview, not a silent rewrite. Buttons say **Defer laundry; keep 8:20** and **Keep all tasks; review 8:28**.

After approval: task remains in deferred work; the original deadline stays visible; completed work stays anchored. Say **Based on your estimates**, not **Guaranteed on time**.

## Judge challenge rehearsal

“Is this just an LLM checklist?” Change the washer release time and open the actual constraint calculation; show participant capacity and the saved revision.

“What if the chore is essential?” Change its priority and demonstrate that deferral disappears and infeasibility remains.

“What if the user declines?” Save the observed delay, keep current commitments, and display that the goal needs a revision. Never turn the status green after rejection.

“Does Alexa really run this?” Answer precisely: “This submission uses the permitted Alexa+ simulation path. The AI invokes our validated planning tools; it is not an installed Alexa skill.” Update this only if a native integration is actually completed and verified.

“Who wants it?” Explain the recurring departure job and adjacent routine demand. Describe direct household validation as future work. Do not confuse a convincing scenario with validated retention.

## Submission copy direction

One-line pitch: **ReadyBy helps households leave on time by coordinating shared tasks and recovering when the plan changes.**

Lead with customer problem, then show the recovery example, then explain the AI/constraint-engine boundary. Include real implementation details, reproducible tests, integration disclosure, limitations, and factual developer feedback. Screenshots should show the opening plan, infeasible deadline, and approved recovery. No generic “AI-powered productivity revolution” claims or invented quantified impact.
